# Python 第 24 课：Python 篇阶段回顾：从脚本到产品化

## 这一课要解决的问题

前面 23 节课，我们已经从第一个 PDF 合并脚本，一路走到了桌面界面、Web 服务和前端页面。

这中间知识点很多，容易学着学着变成“每节课都听懂了，但不知道它们怎么连起来”。

所以这一课先不急着加新功能。

我们把前面的路线重新顺一遍：

```text
临时脚本 -> 稳定项目 -> GUI 工具 -> EXE 分享
Excel / Word / PDF 工具层 -> API 数据获取 -> Markdown 文档处理
React + pywebview 本地桌面路线
FastAPI + 前端 Web 服务路线
```

你要建立一个整体感觉：

> Python 不是只写脚本，而是把一个个办公动作变成可以复用、可以交付的小工具。

## 第一阶段：先把脚本跑起来

最早的目标很简单：

```text
让 AI 帮我们做出第一个 PDF 合并工具。
```

这一阶段重点不是代码多漂亮，而是先跑通：

- 能找到输入文件。
- 能生成输出文件。
- 能在命令行运行。
- 能处理路径问题。
- 出错时能看到错误信息。

这里你要记住一个基本习惯：

```text
先做最小可运行版本，再慢慢变稳定。
```

不要一开始就要求 AI 做完整软件。

先让它完成一件很小的事，然后再补路径、配置、日志、界面和打包。

## 第二阶段：从临时脚本到稳定项目

脚本能跑以后，就要开始整理项目。

我们前面反复练过这些动作：

- 新建清楚的项目目录。
- 使用虚拟环境。
- 用 `requirements.txt` 记录依赖。
- 用 `README.md` 说明怎么运行。
- 用 `.gitignore` 忽略临时文件。
- 用 Git 保存版本。
- 把输入、输出、配置分开。

一个小工具如果要长期使用，不能只靠“我记得怎么运行”。

它至少要做到：

```text
别人打开项目，也能看懂放什么文件、点哪里运行、结果在哪里。
```

## 第三阶段：把业务逻辑沉到工具层

后面课程里，我们开始做 Excel、PDF、Word 工具箱。

这里最重要的原则是：

```text
业务逻辑不要写死在界面里。
```

更好的结构是：

```text
core/ 或 excel/ 或 pdf/ 或 word/
  负责真正处理文件和数据

gui/ 或 web/ 或 api/
  负责接收用户操作和展示结果
```

比如：

- PDF 合并函数应该放在 `pdf/` 或 `core/`。
- Excel 清洗函数应该放在 `excel/`。
- Word 提取函数应该放在 `word/`。
- PySide6、React、FastAPI 只是不同入口。

这样做的好处是：

> 同一个工具函数，可以被命令行、桌面窗口、Web 页面、AI Agent 重复调用。

## 第四阶段：Excel、Word、PDF 的处理路线

办公自动化里常见文件主要是：

- PDF
- Excel
- Word
- Markdown

它们的处理方式不一样。

PDF 适合做：

- 合并。
- 拆分。
- 提取文本。
- 生成附件或报告。

Excel 有两条路线：

```text
XML 路线：openpyxl / pandas 等库直接读写文件
COM 路线：xlwings 调用本机 Excel 程序自动操作
```

Word 也有两条路线：

```text
XML 路线：python-docx 直接读写 docx
COM 路线：调用本机 Word 程序自动操作
```

选择路线时先问一句：

```text
我只是处理文件内容，还是必须调用 Office 软件本身？
```

如果只是读写数据，优先用文件处理库。

如果必须依赖 Office 的实际功能，再考虑 COM。

## 第五阶段：API 与外部数据

从汇率 API、AkShare 到 MinerU，我们开始让 Python 不只处理本地文件，也能调用外部服务。

这里要记住几个关键词：

- 请求地址。
- 请求参数。
- 返回 JSON。
- 错误处理。
- API Key。
- 请求日志。

调用 API 时，不要只盯着“拿到结果”。

还要看清楚：

```text
我发出了什么请求？
对方返回了什么？
失败时我怎么知道原因？
结果能不能继续被程序处理？
```

## 第六阶段：Markdown 和提示词

Markdown 是这一阶段很重要的中间格式。

它的作用是：

```text
把文档内容整理成 AI 和人都容易阅读的结构。
```

比如 MinerU 可以把 PDF 解析成 Markdown。

后面我们可以继续让 AI 阅读 Markdown，输出摘要、风险点、结构化数据，甚至写入 Excel。

所以你可以把 Markdown 理解成：

> 文档处理和 AI 分析之间的桥。

## 第七阶段：两条产品化路线

前两课我们看了两条路线。

第一条是本地桌面路线：

```text
React 前端 -> pywebview 桥接 -> Python 工具层
```

适合：

- 自己电脑使用。
- 处理本地文件。
- 调用本机 Excel / Word。
- 打包成桌面软件给同事。

第二条是 Web 服务路线：

```text
React / HTML 前端 -> HTTP 请求 -> FastAPI -> Python 工具层
```

适合：

- 多人访问。
- 浏览器访问。
- 局域网部署。
- 被脚本、系统或 AI Agent 调用。

两条路线不是谁替代谁。

它们只是不同入口。

真正稳定的资产仍然是：

```text
Python 工具层
```

## 你要形成的项目判断

以后拿到一个需求，可以按这几个问题判断：

1. 这个需求能不能先做成一个命令行脚本？
2. 输入是什么文件？输出是什么文件？
3. 核心处理逻辑应该放在哪个工具层？
4. 用户需要桌面窗口，还是浏览器页面？
5. 是单机使用，还是多人访问？
6. 有没有外部 API、AI 模型或 Office COM？
7. 结果要给人看，还是要给程序继续处理？

这些问题比具体语法更重要。

它们决定项目会不会越做越清楚。

## 一个通用开发顺序

以后做办公自动化工具，可以按这个顺序推进：

```text
1. 用一句话写清需求
2. 准备 input/output 示例
3. 让 AI 先做最小脚本
4. 把核心逻辑整理成函数
5. 增加错误处理和日志
6. 写 README 和 requirements.txt
7. 选择入口：命令行 / GUI / Web / pywebview
8. 测试几个真实文件
9. 再考虑打包、分享或部署
```

不要跳过前几步直接做大界面。

界面只是入口，工具层才是核心。

## 今天要记住

前面所有课程可以压缩成一句话：

> 用 Python 把办公动作变成稳定工具，再选择合适的入口交给别人使用。

入口可以换：

```text
命令行
PySide6
React + pywebview
FastAPI + 前端
AI Agent
```

但核心逻辑要尽量稳定、清楚、可复用。

下一课我们会用一个小案例，把这些知识点再串一次。

案例不追求复杂功能，而是追求完整链路：

```text
Python 后端启动 Web 页面 -> 上传文件 -> 后端处理 -> 返回 JSON -> 前端展示结果
```
