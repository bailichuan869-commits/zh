## 方案依据

- 阿里云百炼：文档解析与切片、标签和元数据过滤、Top-K、阈值、重排、拒答、至少 100 组问题的评测基线、持续评估和日志监控。

## 长期架构

1. `raw/` 保存不可由 Wiki 反向覆盖的事实来源，二进制原件必须具备可检索 Markdown 门面。
2. `wiki/` 保存结构化知识、案例、问答、来源摘要和导航；法规保留合并全文和条文锚点，不按一条一个知识页拆分。
3. 所有知识资产统一记录来源、类型、领域、主题、标签、权威等级、版本、生效区间、生命周期和复核状态。
4. `general-search`、`answer-current`、`case-review`、`learning` 四个 profile 控制检索范围和证据要求。
5. 默认检索路线保持章节级 FTS5/BM25、编号匹配、元数据过滤和确定性权威排序。
6. 答疑必须返回来源、版本、生效日期、章节、片段、来源 URL、得分和追溯路径；证据不足时拒答。
7. Agent 承担摄入、整理和复核；普通写入保持 preview -> 明确确认 -> 哈希校验 -> commit。`agent-reviewed` 与人工批准分开记录。
8. 文档、问答、案例和结构化 CSV/JSON 使用同一资产模型；没有真实结构化查询需求前，不建设独立业务数据库。

## 评测长期标准

- 默认指标为题级 Recall@5：每个问题至少一个预期来源进入前 5 条即视为召回。
- 完整知识与 reviewed-only 两套评测都必须运行；阶段 2 以 reviewed-only Recall@5 >= 90% 为硬门禁。
- 评测集至少 100 题，覆盖会计、审计、法律、政策、职业道德、案例、历史版本和拒答边界。
- 用例逐步增加预期来源、禁止来源、版本日期、必须引用点和必须拒答标记。
- 必须输出 domain、category、tier 等分层统计，避免总分掩盖单一领域退化。
