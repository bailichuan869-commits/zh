# Agent第02课：Skill 使用和创建

## 从一个审计场景开始

假设我们正在做年审项目，拿到了一张营业收入明细表。

表里可能有这些字段：

```text
月份、客户、产品线、收入金额、上年同期收入、预算收入、毛利率、回款金额
```

我们希望 AI 帮我们执行营业收入的分析性程序。

如果只是这样问：

```text
请帮我分析一下收入有没有异常。
```

AI 可能会回答：

```text
收入整体增长，部分月份波动较大，建议关注异常客户。
```

这类回答不能说完全错，但审计价值比较有限。

审计里的分析性程序，不只是描述数据有没有变化。它更关心这些问题：

- 本期收入和上年同期相比是否异常。
- 本期收入和预算相比是否异常。
- 月度收入趋势是否符合业务规律。
- 收入是否集中在少数客户。
- 不同产品线的收入结构是否发生明显变化。
- 收入增长是否伴随毛利率异常变化。
- 收入增长是否有对应回款支持。
- 期末收入是否突然增加。
- 是否存在收入截止性风险、真实性风险、关联方交易风险。
- 是否需要追加函证、截止测试、合同检查、期后回款检查等程序。

也就是说，分析性程序不是简单地“看一眼数据”。

它需要把数据波动继续往下推：

```text
数据异常 -> 可能原因 -> 审计风险 -> 进一步审计程序
```

这条链路，正是 Skill 适合解决的问题。

## Skill 解决的不是“AI 不够聪明”

Skill 可以理解为：

> 给 AI 准备的一套可复用工作流。

它不是一个神奇插件，也不是让 AI 突然拥有新的专业能力。

它主要解决的是这些问题：

- 同一类任务，每次都要重新告诉 AI 怎么做。
- 提示词越写越长，上下文越来越重。
- 不同人问 AI，得到的结果风格和质量不一致。
- 资深人员脑子里的判断路径，很难稳定传给新人。
- AI 容易停留在表面总结，没有按专业流程继续追问。

以营业收入分析性程序为例，Skill 的价值不是帮我们算一个同比、环比。

真正有价值的是：

> 让 AI 按审计人员的分析路径，把收入波动转化成审计关注点。

## Prompt 和 Skill 的区别

Prompt 更像这一次的任务指令。

例如：

```text
请帮我分析这张收入表。
```

Skill 更像一份长期可复用的作业指导书。

例如：

```text
当用户要求对营业收入执行审计分析性程序时，
先识别数据口径，
再执行趋势分析、结构分析、比率分析和回款匹配分析，
然后把异常波动转化为审计风险和进一步程序建议。
```

可以简单理解为：

```text
Prompt 解决这一次怎么问。
Skill 解决以后遇到同类任务，AI 应该按什么方法做。
```

## 一个收入分析性程序 Skill 示例

下面是一个简化版 Skill 示例。

```markdown
---
name: revenue-analytical-procedure
description: 当用户需要对营业收入、成本、毛利率、费用或其他财务数据执行审计分析性程序，识别异常波动、审计风险并形成底稿说明时使用。
---

# 营业收入分析性程序

## 分析步骤

1. 识别分析对象、期间、数据口径和可用字段。
2. 执行基础比较：
   - 本期与上期比较
   - 本期与预算比较
   - 月度趋势分析
   - 产品、客户、地区结构分析
3. 识别异常：
   - 期末月份收入突增
   - 收入增长但回款未同步增长
   - 收入增长但毛利率异常下降或上升
   - 少数客户贡献大部分收入
   - 新客户或异常大额订单
   - 与历史季节性不一致
4. 将异常转化为审计关注点：
   - 收入确认是否真实
   - 收入是否记录于恰当期间
   - 是否存在提前确认收入
   - 是否存在关联方或异常交易
   - 是否需要追加函证、截止测试、合同检查或期后回款检查
5. 输出时不得只描述数据，必须说明审计含义。
6. 如果数据不足，明确列出需要补充的数据。

## 输出结构

输出按以下结构组织：

1. 数据概况
2. 已执行的分析维度
3. 主要波动
4. 异常识别
5. 可能原因
6. 审计风险
7. 建议追加程序
8. 初步结论
```

有了这样的 Skill，再让 AI 分析收入数据时，它就不只是回答：

```text
12 月收入较高，需要关注。
```

而是更可能沿着审计分析路径继续往下写：

```text
12 月收入显著高于全年月均水平，主要由 A 客户和 B 客户贡献。
同期回款比例低于全年平均水平，且毛利率高于历史区间。
该波动可能涉及收入截止、交易真实性和期后回款风险。
建议追加检查 12 月大额销售合同、出库单、验收单、发票、期后回款，并扩大截止测试样本。
```

这个差别很重要。

没有 Skill，AI 可能只是总结数据。

有了 Skill，AI 会按预先设定的审计工作流继续判断。

## 为什么分析性程序适合做成 Skill

分析性程序很适合用来理解 Skill，因为它有几个特点。

第一，它是高频任务。

很多审计项目、很多报表科目都会做分析性程序。

第二，它有固定方法。

趋势分析、结构分析、比率分析、预算比较、历史比较，这些路径都可以沉淀。

第三，它需要专业判断。

看到波动只是第一步，更重要的是判断这个波动是否对应审计风险。

第四，它需要标准输出。

分析性程序的结果不是闲聊结论，而是要进入底稿、复核、沟通和后续审计程序。

所以，Skill 不是把提示词包装得更漂亮。

它是在把一个可重复的专业工作流交给 AI 执行。

## 为什么 Skill 要渐进式加载

如果我们只有一个 Skill，问题还不明显。

但真实使用时，我们可能会有很多 Skill。

例如：

- Excel 清洗 Skill。
- PDF 解析 Skill。
- 合同审查 Skill。
- 审计抽样 Skill。
- 收入分析性程序 Skill。
- 底稿生成 Skill。
- 公众号写作 Skill。
- 代码审查 Skill。

如果以后有 100 个 Skill，能不能把它们的完整内容一次性全部塞进上下文？

一般不应该这样做。

因为 AI 每次回答问题前，都会先处理当前上下文。

上下文可以理解为 AI 的临时工作台。

工作台上要放很多东西：

```text
系统规则
当前对话
用户上传的文件内容
项目说明
工具说明
正在处理的代码或表格
可能用到的 Skill
```

如果把 100 个 Skill 的完整内容都放进来，会出现三个问题。

第一，装不下。

每个 Skill 可能有几百到几千字。

100 个 Skill 加起来，可能就是几十万字。

上下文窗口不是无限的。无关 Skill 放得越多，真正的任务资料就越容易被挤出去。

第二，变慢、变贵。

上下文不是免费的。

放进去的每一句话，AI 都要处理。

这次任务可能只需要一个收入分析性程序 Skill，但如果把另外 99 个 Skill 也一起放进去，它们也会占用上下文、计算时间和成本。

第三，更容易混乱。

上下文太多，不只是“放不下”，还会让 AI 分不清当前到底该听谁的。

比如用户只是想分析营业收入，但上下文里同时放着合同审查、PDF 解析、公众号写作、代码审查等规则。

AI 可能会被无关规则干扰：

```text
本来要做收入分析，却套用了合同审查结构。
本来要输出审计风险，却写成了文章摘要。
本来只需要读取 Excel，却被 PDF 处理规则影响。
```

所以，Skill 需要渐进式加载。

渐进式加载的意思是：

```text
第一层：先让 AI 看到所有 Skill 的名字和简短描述
第二层：根据当前任务判断应该使用哪个 Skill
第三层：只加载相关 Skill 的 SKILL.md
第四层：如果还需要，再读取 references / scripts / assets
```

也可以理解为：

> 不是把 100 本手册全摊开，而是先看目录，确定需要哪一本，再翻到对应章节。

在 Skill 里，`name` 和 `description` 就像目录。

它们帮助 AI 判断：

```text
这个任务和哪个 Skill 有关？
现在是否需要打开这个 Skill 的详细说明？
```

匹配到以后，AI 才会读取对应的 `SKILL.md`。

如果 `SKILL.md` 里还引用了更详细的资料，AI 再按需读取 `references`、调用 `scripts`，或者使用 `assets`。

可以把这个过程画成这样：

```text
用户任务
  ↓
查看 Skill 的 name + description
  ↓
判断哪个 Skill 相关
  ↓
加载相关 Skill 的 SKILL.md
  ↓
需要时再加载 references / scripts / assets
  ↓
开始执行任务
```

一句话总结：

> 渐进式加载，就是让 AI 先看目录，再翻书，而不是每次把整套图书馆搬进上下文。

## 创建 Skill 时要注意什么

创建一个 Skill 时，至少要想清楚三件事。

第一，触发场景要清楚。

AI 要知道什么时候应该使用这个 Skill。

例如：

```text
当用户要求对收入、成本、费用、毛利率等财务数据执行审计分析性程序时使用。
```

第二，工作流要清楚。

不要只写“帮我分析收入”。

要写清楚先做什么、再做什么、发现异常后怎么继续追问。

第三，输出标准要清楚。

审计场景里尤其要避免空泛总结。

可以要求 AI 必须输出：

- 数据概况。
- 分析维度。
- 异常波动。
- 审计含义。
- 进一步程序。
- 证据不足时需要补充的资料。

## 小结

Prompt 解决这一次的问题。

Skill 沉淀下一次也能复用的方法。

放到审计场景里，Skill 的作用不是替代审计判断，而是把审计人员稳定、重复、可复核的分析路径，沉淀成 AI 可以执行的工作流。
