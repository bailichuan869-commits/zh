# Python 第 27 课：Agent 工具调用和固定代码边界判断

## 今天先看一种很直观的工具调用

上一节我们搭了合同抽取 harness 的第一版。

现在我们已经有了这条基本链路：

```text
合同 Markdown
-> AI 阅读合同
-> 输出合同摘要和关键条款
-> 保存日志
```

接下来很自然会想到：

```text
能不能给 Agent 一个 Excel 工具，让它抽取完合同后直接调用工具生成 Excel？
```

可以。

这节课的演示，就可以先这样做。

也就是：

```text
给 Agent 一个 generate_excel 工具
让 Agent 抽取合同字段
再让 Agent 自己调用 generate_excel 生成 Excel
```

这样演示的好处是很直观：

```text
你能看到 Agent 不只是聊天。
它真的可以调用我们写好的 Python 工具。
```

但是演示完以后，要立刻做一个复盘。

因为：

> 能做成 Agent tool，不代表它就是当前场景的最优做法。

今天这节课的重点不是“凡事都做成 Agent tool”，而是学会判断：

> 哪些事情应该交给 Agent 调用工具，哪些事情应该由我们自己写固定代码完成。

这个判断非常重要。

Agent 不是越多工具越高级。

很多时候，流程越固定，越应该用普通代码。

所以这节课分成两层：

```text
第一层：演示 Agent 调用 Excel 工具，理解 tool calling。
第二层：复盘这个设计，判断生产项目里是否应该改成固定代码导出 Excel。
```

## 两种实现路线

同一个合同抽取需求，可以有两种实现方式。

### 路线一：AI 只负责抽取 JSON，网页或后端固定代码生成 Excel

流程是：

```text
上传合同
-> 转成 Markdown
-> 读取字段配置
-> AI 按字段配置抽取 JSON
-> 网页或后端把 JSON 转成表格
-> 固定代码导出 Excel
```

这里 AI 只负责最需要理解能力的部分：

```text
从合同 Markdown 中找到字段内容。
```

生成 Excel 是确定性动作。

只要 JSON 结构固定，网页或后端就可以稳定地把它转成 Excel。

这种方式更适合我们当前的合同助手。

因为用户的目标很明确：

```text
我要从一份合同里按字段配置抽取内容，并导出 Excel。
```

不需要 Agent 自己决定“要不要生成 Excel”。

我们已经知道最后一定要生成 Excel。

所以这一步写成固定代码更稳。

### 路线二：把 Excel 写入能力做成 Agent tool

流程是：

```text
上传合同
-> 转成 Markdown
-> Agent 读取合同
-> Agent 读取字段配置
-> Agent 抽取字段
-> Agent 决定调用 Excel 工具
-> Excel 工具生成文件
```

这种方式也能做。

这就是本节课可以先演示的版本。

它适合帮助你看懂：

```text
什么是工具
Agent 怎么选择工具
工具参数怎么传
工具结果怎么返回
事件日志里怎么看 tool call
```

但它更适合任务不固定的场景。

比如用户说：

```text
请分析这个文件夹里的合同。
如果有金额和付款条款，就生成 Excel 汇总。
如果只是制度文件，就生成 Markdown 摘要。
如果发现风险条款，再单独生成一份风险提示。
```

这时候 Agent 需要自己判断：

```text
要不要读文件夹
要不要读某个文件
要不要写 Excel
要不要写 Markdown 报告
要不要调用其他工具
```

这种场景才更适合工具调用。

## 演示版和最优版要分开看

本节演示可以用路线二：

```text
Agent 抽取字段
Agent 调用 Excel 工具
Excel 工具生成文件
```

这个版本的教学价值很高。

因为你能看到完整的 Agent tool 调用过程：

```text
TOOL_CALL_START
TOOL_CALL_DELTA
TOOL_RESULT_TEXT_DELTA
TOOL_RESULT_END
```

但是如果从产品稳定性看，当前合同助手更推荐路线一：

```text
AI 抽取 JSON
固定代码生成 Excel
```

这就是一个很重要的工程判断：

```text
演示时可以用 tool 帮大家理解 Agent。
真正做产品时，要判断这一步是不是应该交给 Agent。
```

## 当前合同助手更推荐哪条路线

当前这个合同助手，我更推荐先用路线一：

```text
AI 抽取 JSON
固定代码生成 Excel
```

原因很简单：

- 用户目标固定。
- 输出格式固定。
- Excel 生成是确定性动作。
- 固定代码更容易测试。
- 出错更容易排查。
- 前端可以直接预览 JSON 和表格。

也就是说：

```text
AI 负责理解。
固定代码负责交付。
```

这个分工更清楚。

不要为了使用 Agent tool，而把所有步骤都交给 Agent。

## 什么时候应该用固定代码

如果一件事情满足这些特点，优先用固定代码：

| 判断问题 | 如果答案是“是” |
|---|---|
| 流程是不是固定的？ | 用固定代码 |
| 输入输出格式是不是明确的？ | 用固定代码 |
| 是否不需要 AI 判断下一步？ | 用固定代码 |
| 是否涉及文件保存、表格导出、格式转换？ | 通常用固定代码 |
| 是否需要稳定、可测试、可复现？ | 用固定代码 |

比如合同助手里的这些动作：

```text
把 JSON 转成表格
把表格导出 Excel
把日志保存到文件
把上传文件保存到指定目录
把 Markdown 内容传给模型
```

都可以优先用固定代码。

固定代码不是“不智能”。

固定代码是可靠性。

## 什么时候应该用 Agent tool

如果一件事情满足这些特点，可以考虑做成 Agent tool：

| 判断问题 | 如果答案是“是” |
|---|---|
| Agent 是否需要自己决定下一步做什么？ | 可以用 tool |
| 用户任务是否比较开放？ | 可以用 tool |
| 工具是否是一个可复用能力？ | 可以用 tool |
| Agent 是否需要在多个工具中选择？ | 可以用 tool |
| 是否需要根据中间结果继续行动？ | 可以用 tool |

比如：

```text
列出某个文件夹里的合同
按用户要求选择读取哪些合同
根据文档类型决定生成摘要还是 Excel
发现缺少字段配置时提示用户补充
根据分析结果生成风险报告
在多个输出工具中选择一个
```

这些才更像 Agent tool 的使用场景。

因为 Agent 需要判断、选择、调度。

## 演示时可以怎么做

为了看懂工具调用，本节课可以先演示这个流程：

```text
1. 网页上传合同。
2. 配置需要抽取的字段。
3. 后端把合同 Markdown 和字段配置发给 Agent。
4. Agent 抽取字段。
5. Agent 调用 generate_excel 工具。
6. 前端显示工具调用日志。
7. 前端提供 Excel 下载。
```

这里要重点观察：

```text
Agent 是什么时候决定调用 generate_excel 的？
它传给工具的参数是什么？
工具返回了什么？
前端是怎么拿到 Excel 文件名的？
```

这能帮助你理解工具调用机制。

## 复盘时更推荐怎么做

演示完以后，建议把当前合同助手改成这个更稳定的流程：

```text
1. 网页上传合同。
2. 后端或已有工具把合同转成 Markdown。
3. 网页让用户配置要抽取的字段。
4. 后端把 Markdown + 字段配置发给 AI。
5. AI 返回结构化 JSON。
6. 网页预览 JSON 对应的表格。
7. 点击“导出 Excel”时，由网页或后端固定代码生成 Excel。
```

这个版本里，不需要给 Agent 一个 Excel 工具。

因为：

```text
Excel 一定要生成。
Excel 格式是固定的。
把 JSON 转 Excel 不需要 AI 判断。
```

这就是一个很好的判断示例。

## 今天要让 AI 帮我们做什么

今天可以让 AI 先帮我们做一个演示版本：

> Agent 抽取字段后，调用 `generate_excel` 工具生成 Excel。

这个演示版本要有：

```text
一个合同字段抽取页面
一个字段配置区域
一个 AI 抽取按钮
一个 Agent 事件日志区域
一个 generate_excel 工具
一个 Excel 下载按钮
```

然后再让 AI 帮我们复盘并说明：

> 如果要做成更稳定的产品，可以改成 AI 只负责抽取 JSON，网页或后端固定代码负责生成 Excel。

也就是说，这节课不是只得到一个功能，而是得到一个判断：

```text
演示版：Agent 调 Excel tool，方便理解 tool calling。
产品版：AI 抽 JSON + 固定代码导 Excel，更稳定。
```

## 最优版本应该长什么样

如果按产品稳定性来设计，合同助手更推荐这个模式：

```text
一个合同字段抽取页面
一个字段配置区域
一个 AI 抽取按钮
一个 JSON / 表格预览区
一个导出 Excel 按钮
一段固定的 JSON 转 Excel 代码
一份运行日志
```

页面逻辑应该是：

```text
选择合同 Markdown
填写字段配置
点击“开始抽取”
后端调用 AI 返回 JSON
前端把 JSON 渲染成表格
点击“导出 Excel”
固定代码把表格导出为 Excel
```

## JSON 结果应该长什么样

AI 返回的 JSON 可以继续使用通用结构：

```json
{
  "contract_file": "sample_contract.md",
  "fields": [
    {
      "field_key": "amount",
      "field_name": "合同金额",
      "value": "人民币 120000 元",
      "evidence": "合同总金额为人民币 120000 元。",
      "confidence": "high",
      "missing_reason": ""
    }
  ]
}
```

固定代码只需要把 `fields` 展开成表格：

| 合同文件 | 字段编码 | 字段名称 | 抽取结果 | 原文依据 | 置信度 | 缺失原因 |
|---|---|---|---|---|---|---|
| sample_contract.md | amount | 合同金额 | 人民币 120000 元 | 合同总金额为人民币 120000 元。 | high |  |

这个转换过程不需要 AI。

## 什么时候再引入 Excel tool

后面如果合同助手变成更开放的 Agent，可以再引入 Excel tool。

比如用户不是点击固定按钮，而是直接输入任务：

```text
请分析 input/contracts 文件夹。
合同类文件生成 Excel 汇总。
制度类文件生成 Markdown 摘要。
如果发现高风险条款，再单独生成风险清单。
```

这时 Agent 需要决定：

```text
读取哪些文件
每个文件属于什么类型
生成什么输出
什么时候调用 Excel 工具
什么时候调用 Markdown 报告工具
```

这种场景再讲工具调用就很自然。

## 今天要记住

Agent tool 不是越多越好。

判断标准是：

```text
需要 AI 判断和选择的动作，可以考虑做成 tool。
流程固定、结果确定的动作，优先写成固定代码。
```

合同助手当前版本里：

```text
AI 抽取 JSON：适合大模型。
JSON 转 Excel：适合固定代码。
```

这个边界比“全部交给 Agent”更重要。

## 做完以后你应该能

- 说清 Agent tool 和固定代码的区别。
- 判断什么时候需要把能力做成 tool。
- 判断什么时候应该用固定代码完成。
- 解释为什么当前合同助手不一定需要 Excel tool。
- 设计“AI 抽取 JSON + 固定代码导出 Excel”的合同助手流程。
- 让 AI 帮你生成合同字段抽取页面和 Excel 导出功能。
