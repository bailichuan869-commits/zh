# Agent第01课：Agent 入门概述

## 这一节要解决什么

很多人已经不陌生 AI。

平时可能会用：

- 豆包；
- DeepSeek；
- 千问；
- Kimi；
- ChatGPT；
- Claude；
- 各种写作、总结、翻译、编程工具。

但是一聊到 Agent，很多概念就会突然变多：

```text
大模型
TOKEN
上下文
记忆
知识库
提示词
工具
MCP
ReAct
Workflow
Skill
上下文工程
```

这些词如果分开听，会比较散。

这一节不深入讲底层算法，也不追新名词，而是先把 Agent 这套东西串起来。

你先知道：

> Agent 到底是什么，它和普通聊天 AI 有什么区别，以及它在财审场景里能做什么。

## 本节你会学到

- 为什么现在要理解 Agent。
- Agent 和普通聊天 AI 的区别。
- Agent 可以拆成哪几个部分。
- 大语言模型到底擅长什么、不擅长什么。
- TOKEN 和上下文为什么重要。
- 记忆、知识库、Skill 分别是什么。
- 工具和 MCP 为什么让 AI 从“会说”变成“会干活”。
- ReAct 循环是怎么让 Agent 一步步做任务的。
- Workflow 和 Agent 应该怎么选。
- 财审行业里使用 Agent 的两条路线。

## 为什么现在要懂 Agent

过去我们用 AI，很多时候是：

```text
问一句 → 答一句
```

比如：

- 帮我总结；
- 帮我润色；
- 帮我翻译；
- 帮我写一段话；
- 帮我解释一个概念。

这种使用方式更像一个高级聊天框。

但现在越来越多的 AI 已经不只是在回答问题。

它可以：

- 查资料；
- 读文件；
- 调工具；
- 操作 Excel；
- 读取 PDF；
- 写入 Word；
- 跑流程；
- 遇到错误后自己修正；
- 根据结果继续下一步。

也就是说，AI 正在从：

```text
会回答
```

走向：

```text
会干活
```

这就是理解 Agent 的意义。

## 一个财审案例：截止测试 Agent

假设现在有一个截止测试任务。

资料文件夹里有：

- 一个空的 Excel 底稿；
- 两个扫描版 PDF 单据；
- 一个截止测试的任务说明或 Skill。

你给 Agent 的指令可能只有一句：

```text
帮我进行截止测试，资料在对应文件夹中。
```

接下来它可能会自己做这些事：

1. 读取截止测试的任务说明。
2. 打开 Excel 底稿，理解底稿结构。
3. 读取 PDF 扫描件。
4. 从 PDF 中提取单据信息。
5. 判断截止日前、截止日后的明细应该填到哪里。
6. 调用 Excel 工具，把结果写入底稿。
7. 写出测试结论。
8. 如果你指出填错位置，它可以再调用工具修正。

这个过程已经不是简单聊天。

它是在：

```text
理解任务 → 读取资料 → 调用工具 → 写入结果 → 根据反馈修正
```

这就是 Agent 的雏形。

## Agent 可以拆成三部分

你可以先把 Agent 理解成三层：

```text
大模型
工具和知识
Agent 框架
```

### 1. 大模型：负责理解和生成

大模型是 Agent 的“大脑”。

它负责：

- 理解你的问题；
- 理解资料；
- 推理下一步；
- 生成回答；
- 判断该调用什么工具。

可以把它理解成一个会读、会写、表达能力很强的实习生。

### 2. 工具和知识：负责获取信息和执行动作

光有大脑还不够。

如果没有工具，AI 只能说话。

有了工具后，它才能：

- 读 Excel；
- 写 Excel；
- 读 PDF；
- 查数据库；
- 调接口；
- 操作文件；
- 运行代码。

工具让 Agent 有了“手”。

知识库、文件、Skill 则让 Agent 有了“资料”和“手册”。

### 3. Agent 框架：负责把流程串起来

Agent 框架不是一个模型。

它更像一个系统，把这些东西组织起来：

- 模型；
- 工具；
- 任务；
- 上下文；
- 中间步骤；
- 错误处理；
- 最终结果。

所以 Agent 不是一个单独按钮，也不是一个单独模型。

它是一套工作方式。

## 大语言模型是什么

大语言模型可以理解成：

> 一个读过大量文本、会总结、会改写、会翻译、会分类、会生成内容的实习生。

它很厉害，是因为在训练阶段见过大量文本，学会了很多语言模式和任务模式。

但是要记住边界：

> 它不是天然知道你项目的真实情况。

如果你不给它底稿、合同、发票、凭证、审计程序、项目背景，它只能根据训练中见过的模式往下推。

所以它很会说，不代表它一定说得对。

## 模型也有类型差异

不同模型能力不一样。

有的模型只能处理文字。

有的模型可以看图片。

有的模型可以听音频。

有的模型可以处理视频。

可以简单分成：

| 类型 | 能力 |
| --- | --- |
| 单模态模型 | 主要处理文字 |
| 多模态模型 | 可以处理文字、图片、音频等多种输入 |

比如扫描合同、扫描发票、截图底稿，就更适合多模态模型或搭配 OCR / 文档解析工具。

选模型时也不是越贵越好。

你要看任务：

- 简单任务：可以用速度快、成本低的模型。
- 复杂推理：尽量用能力更强的模型。
- 编程任务：优先选择编程能力强的模型。
- 图片理解：要选择支持视觉能力的模型。

## 模型不是“真的懂了”，它是在预测

大模型生成回答，本质上是一个接一个地预测下一个 token。

它不是先像人一样完整理解一遍，再把答案说出来。

它更像是：

```text
看前面的内容
  ↓
判断哪些内容重要
  ↓
预测下一个 token
  ↓
再继续预测下一个 token
```

这解释了一个很重要的问题：

> 为什么模型有时会一本正经地说错？

因为它是在预测，而预测不等于事实校验。

只要前后话能接上，它就可能生成一个听起来合理、但实际上不存在的内容。

这就是常说的幻觉。

## 什么是 TOKEN

TOKEN 是模型处理文字的基本计量单位。

可以类比：

- 用电按“度”计费；
- 快递按“重量”计费；
- 模型按“TOKEN”处理和计费。

但 TOKEN 不等于汉字数，也不等于英文单词数。

模型会先通过 tokenizer 把文字切成它能处理的基本单元。

例如一句中文，可能几个字合成一个 token，也可能一个标点单独算一个 token。

你不需要精确计算每句话有几个 token。

你只要知道：

> 输入越多、历史越长、工具返回越大，消耗的 token 就越多。

## 什么是上下文

上下文是 Agent 当前这一轮任务中能看到的所有材料。

包括：

- 系统提示词；
- 用户这次输入的问题；
- 前面的聊天记录；
- 上传的文件；
- 知识库检索结果；
- Skill 内容；
- 工具调用结果；
- 工具报错信息；
- 中间思考和执行记录。

模型并不是天然记得你之前说过什么。

很多对话系统的做法是：

> 每次你发新消息时，客户端把前面的历史记录和新消息一起打包，再发给模型。

所以对话越长，上下文越长。

上下文越长，会带来几个问题：

- 成本变高；
- 速度变慢；
- 模型更容易抓偏重点；
- 重要信息可能被淹没；
- 工具报错和无关信息会污染上下文。

这也是为什么要讲上下文工程。

## 上下文不是越长越好

现在很多模型支持几十万 token 的上下文。

这很有用，但不代表你应该把所有东西都塞进去。

上下文太长、太杂、太乱，模型会更难抓住重点。

可以把上下文理解成你给实习生看的资料包。

资料包里如果混着：

- 旧版本底稿；
- 无关邮件；
- 已经失败的工具调用；
- 重复内容；
- 不清楚的规则；
- 一堆不相关文件；

实习生反而更容易判断错。

所以更好的做法是：

```text
给它正确的、干净的、当前任务需要的上下文。
```

## 记忆、知识库、Skill 有什么区别

这三个词很容易混。

可以先这样理解：

| 概念 | 解决什么问题 |
| --- | --- |
| 记忆 | 保存长期偏好、长期事实、历史总结 |
| 知识库 | 从大量资料中检索当前相关内容 |
| Skill | 固化某类任务的操作手册和工作流 |

### 记忆

记忆不是模型脑子里真的长出了记忆。

很多系统的实现方式是：

```text
把历史信息提炼成摘要
  ↓
保存起来
  ↓
下次对话时再注入上下文
```

所以记忆本质上还是在影响上下文。

### 知识库

知识库通常用 RAG 检索。

它不是一次性把全部资料塞给模型。

而是：

```text
用户提问
  ↓
系统去知识库里检索相关片段
  ↓
把相关片段放进上下文
  ↓
模型基于这些内容回答
```

知识库适合放：

- 制度；
- 指引；
- 历史案例；
- IPO 问询资料；
- 审计方法论；
- 项目资料。

### Skill

Skill 可以理解成能力包或操作手册。

比如：

- 截止测试怎么做；
- 监盘怎么做；
- 抽凭怎么做；
- 底稿复核怎么做；
- 报告校对怎么做。

Skill 里可以写：

- 任务目标；
- 操作步骤；
- 输入资料要求；
- 输出格式；
- 异常处理；
- 注意事项；
- 示例。

当用户的任务匹配这个 Skill 时，Agent 会加载它，让模型按这份手册执行。

## 提示词分两类

提示词大致可以分为两类：

```text
系统提示词
用户提示词
```

### 系统提示词

系统提示词通常是系统或智能体预先设置好的规则。

比如：

- 你是谁；
- 你能做什么；
- 你应该遵守什么流程；
- 你能调用哪些工具；
- 输出格式是什么。

它一般每次对话都会带上。

### 用户提示词

用户提示词就是你每次输入的内容。

比如：

```text
帮我做销售费用截止测试。
资料在这个文件夹里。
结果填到这个底稿中。
```

提示词写得好不好，会影响模型拿到的任务是否清楚。

但不要把一切问题都归结为提示词。

很多时候真正重要的是：

- 上下文是否干净；
- 工具是否可用；
- Skill 是否写清楚；
- 输出是否能验证；
- 错了以后怎么纠正。

## 工具让 AI 从会说变成会干活

没有工具时，AI 只能输出文字。

有工具后，它可以执行动作。

比如：

- 读取 Excel；
- 写入 Excel；
- 读取 PDF；
- 抽取扫描件；
- 查数据库；
- 调接口；
- 运行脚本；
- 操作文件。

在截止测试案例中，Agent 能读 PDF、读 Excel、写 Excel，就是因为它有对应工具。

工具让 AI 有了“手”。

## MCP 是什么

MCP 可以理解成工具接入的统一标准。

可以用 USB 来类比：

```text
鼠标、键盘、打印机
  ↓
只要符合 USB 标准
  ↓
插到不同电脑上都能用
```

MCP 也是类似的思路。

如果一个工具按照 MCP 标准开发，那么它就可以更容易接入不同的 AI 客户端和 Agent 框架。

所以日常说 MCP，有时其实是在说：

```text
一个可以被 Agent 调用的工具服务。
```

例如：

- Excel MCP；
- PDF 解析 MCP；
- 数据库查询 MCP；
- 文件操作 MCP。

## ReAct：Agent 是怎么一步步干活的

普通聊天 AI 往往是：

```text
你问一句 → 它答一句
```

Agent 更像：

```text
思考 → 行动 → 观察 → 再思考 → 再行动 → 再观察
```

这就是 ReAct：

- Reasoning：推理；
- Acting：行动。

以截止测试为例：

1. 它先思考任务是什么。
2. 决定先读取 Skill。
3. 读取后发现需要看 Excel 底稿。
4. 调用工具读取 Excel。
5. 发现还需要看 PDF。
6. 调用工具读取 PDF。
7. 根据结果写入底稿。
8. 观察写入是否完成。
9. 如果没完成，继续下一步。
10. 完成后总结。

你看起来只发了一句话，但 Agent 可能已经在内部循环了很多轮。

## Workflow 和 Agent 的区别

Workflow 是固定流程。

Agent 是动态决策。

可以这样类比：

| 类型 | 类比 | 特点 |
| --- | --- | --- |
| Workflow | 火车轨道 | 路线固定，稳定可控，可复现 |
| Agent | 自动驾驶 | 目标固定，路线可变，灵活但不稳定 |

Workflow 适合：

- 固定规则清洗；
- 固定格式汇总；
- 固定步骤重命名；
- 确定性强的批处理。

Agent 适合：

- 资料不固定；
- 步骤需要边做边判断；
- 需要调用多个工具；
- 需要根据中间结果调整路线；
- 开放式分析任务。

在审计场景里，很多任务对准确性要求很高。

所以不是所有事情都适合交给 Agent 自由发挥。

能写成稳定 Workflow 或工具的，往往更适合工具化。

需要灵活判断的，才更适合 Agent。

## Skill 和上下文工程

很多人学 AI，最后只盯着提示词。

但真正做 Agent，不能只靠一次提示词。

Skill 的作用是把一类任务的 SOP 固化下来。

比如截止测试 Skill 可以写：

- 截止日前数据填哪里；
- 截止日后数据填哪里；
- 读取哪些资料；
- 如何判断跨期；
- 输出结论怎么写；
- 常见错误怎么避免。

如果这次 Agent 把截止日前和截止日后填错了，你可以把这个注意事项沉淀进 Skill。

下次做类似任务时，Agent 就能按更新后的 Skill 执行。

这就是迭代。

Skill 本质上也在管理上下文：

- 平时只把 Skill 名称和描述放进上下文；
- 真正需要时，再加载完整 Skill；
- 避免一开始就把所有手册塞进去。

## 上下文工程是什么

上下文工程可以理解成：

> 围绕模型搭建一套让它稳定工作的环境。

包括：

- 给什么资料；
- 不给什么资料；
- 如何写系统提示词；
- 如何组织历史记录；
- 何时加载 Skill；
- 工具结果怎么压缩；
- 错误怎么反馈；
- 输出怎么校验；
- 失败后怎么重试。

可以用一个比喻：

> 模型像马，光有马不够，还要有缰绳。

再强的模型，如果上下文混乱、工具不好用、规则不清楚，也会跑偏。

普通模型如果上下文组织得好，也可能完成很好的结果。

## 财审里使用 Agent 的两条路线

在财审实践中，可以先理解两条路线。

### 路线一：AI 数字助理

把 Agent 当成一个数字助理。

给它配：

- Excel 工具；
- Word 工具；
- PDF 工具；
- 数据库工具；
- 检索工具；
- 审计 Skill；
- 项目资料。

然后让它辅助完成任务。

例如：

```text
帮我做销售费用截止测试。
按截止测试 Skill 执行。
资料在这个文件夹中。
结果填到底稿里。
```

这种路线适合探索：

- 自动读资料；
- 自动填底稿；
- 自动检查；
- 自动总结；
- 自动生成说明。

但要注意复核，因为 Agent 可能出错。

### 路线二：AI 帮你写工具

另一条路线是：

> 不让 Agent 直接做审计任务，而是让 AI 帮你写代码，把稳定高频任务做成工具。

比如：

- Excel 加载项；
- VBA 小工具；
- Python 批处理；
- 底稿辅助工具；
- 文件重命名工具；
- 抽样工具；
- 数据清洗工具。

对于规则稳定、高频重复、输出固定的任务，写成工具往往更可靠。

这两条路线不是对立的。

你可以根据场景选择：

```text
开放、复杂、需要判断 → Agent 数字助理
稳定、重复、规则明确 → AI Coding 写工具
```

## 和 AI 对话要不要很客气

不用纠结“请帮我”“麻烦你”这些礼貌用语。

礼貌当然没问题，但真正影响结果的是：

- 目标是否清楚；
- 输入在哪里；
- 输出要什么格式；
- 约束是什么；
- 遇到异常怎么处理；
- 是否允许调用工具；
- 是否需要先 plan；
- 结果如何验证。

与其堆敬语，不如把任务说清楚。

## 本节记住这十句话

1. Agent 不是单个模型，而是一套让 AI 干活的系统。
2. 大模型负责理解和生成，但不天然知道你的项目事实。
3. 模型是在预测，不是在保证事实正确，所以会有幻觉。
4. TOKEN 决定容量、成本和速度。
5. 上下文就是模型当前能看到的全部资料。
6. 记忆、知识库、Skill 本质上都是在影响上下文。
7. 工具让 AI 从“会说”变成“会做”。
8. MCP 是工具接入的统一标准。
9. Workflow 更稳定，Agent 更灵活。

选一个你熟悉的财审任务，尝试拆成 Agent 视角。

可以选：

- 截止测试；
- 抽凭；
- 费用检查；
- 往来函证；
- 底稿复核；
- 报告校对。

按下面格式写：

| 问题 | 你的答案 |
| --- | --- |
| 任务目标是什么 |  |
| 需要哪些输入资料 |  |
| 需要哪些工具 |  |
| 哪些步骤是固定流程 |  |
| 哪些步骤需要判断 |  |
| 适合 Workflow 还是 Agent |  |
| 有没有必要沉淀成 Skill |  |
| 最终结果如何验证 |  |

这张表写完，你就已经不是在“跟 AI 聊天”，而是在设计一个 Agent 任务。
